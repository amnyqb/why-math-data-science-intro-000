# Model API, command line, MCP server

One set of operations on a model, used by the desktop app's engine, a script, a CI job and an AI agent alike. The engine lives in its own crate, `dynamist-core` (folder `core/`), with no window, file dialog or clipboard code in it. `dynamist` (the app) and `dyn` (the command line, folder `cli/`) are clients of it.

```
core/   dynamist-core   model, equations, simulator, sets, units, checks, validate, ops, diff, io, runner, modules, cld, sensitivity, mdl, xmile
cli/    dyn                command line + MCP server (JSON in, JSON out)
src/    dynamist        the desktop app (screens, spreadsheet import/export, charts)
python/ dynamist        a Python wrapper that calls dyn
```

## Position on formats

The native model (`.sdm`) and the operations language are the primary, complete way to describe a model: sets with parents, key levers, model checks, typed module ports and atomic validated batches have no equivalent in the older formats. **Vensim `.mdl`** is a working bridge in both directions for Vensim users. **XMILE** is older, weaker (flat dimensions, vendor extensions) and complicated, so it is treated as a bridge for reading Stella models, not as a format to build on; its writer is best-effort. Every conversion reports what it could not carry.

## Operations (`ops.rs`)

Every operation, with its fields, an example and when it is refused, is in the [Operations language reference](API-Reference.md), generated by `dyn docs` (an agent gets the same through the MCP tool `describe_api`).

Every change is a batch of operations. A batch is applied to a **copy**, the copy is **validated**, and only a batch that passes becomes the model: all or nothing. Each committed batch is **logged** (who, when, what, warnings left), and can be undone.

| Group | Operations |
|---|---|
| Variables | `add_var`, `remove_var`, `rename_var` (follows equations and checks), `set_equation`, `set_units`, `set_doc`, `set_non_negative`, `set_flow`, `set_table` |
| Arrows | `connect`, `disconnect` (arrows are also made from equations automatically) |
| Settings | `set_setting` (`initial_time`, `final_time`, `time_step`, `time_units`, `method`, `title`) |
| Sets | `add_set`, `set_per`, `set_item_value`, `set_lever` |
| Checks and functions | `add_check`, `remove_check`, `add_function`, `remove_function` |
| Modules | `define_module`, `remove_module`, `instantiate`, `set_instance_param`, `set_instance_input`, `remove_instance` |

Queries (read-only): `info`, `list`, `get`, `dependencies` (causes and uses), `loops`, `structure_notes`.

A **session** keeps the model, the log, undo and redo, and a **gate**: while it is on (the default) a batch whose result has validation *errors* is refused with the list of problems. Warnings never block.

## Validation (`validate.rs`)

`validate(model)` compiles and runs the model and returns structured issues (severity, code, variable, message):

| Code | Severity | Meaning |
|---|---|---|
| `equation` | error | an equation does not read or names something unknown |
| `run` | error | the model compiled but could not run |
| `check` | error | something the model states about itself is broken: a limit, a never-negative test, a reference band or a chain balance (see Model checks) |
| `manifest` | error | the manifest names something the model lacks, or a range is the wrong way round |
| `conservation` | error | a stock changed by something other than its flows |
| `arrow-unused`, `arrow-missing` | warning | an arrow the equation does not use, or the reverse |
| `stock-no-flow` | warning | a stock nothing fills or drains |
| `units` | warning | units that do not fit (below) |

### Units are algebra
Units are read as base units with exponents: `Truck/Day`, `Barrels per Truck`, `1/Day`, `MB*Day`. Sums and comparisons need equal dimensions; products and quotients combine them; `SMOOTH`, `DELAY` and friends keep their input's; `ZIDZ(a, b)` is a/b; `SQRT` halves; `LN` and `EXP` give nothing. A variable's declared units must be those of its equation, and a flow's units per time must be its stock's. What cannot be known (no units, a function not listed) is never reported. A rate may meet its amount (MB and MB/Day) unless you ask for `warnings_strict`. Scale is not tracked: MB, Mbbl and barrel are one kind of thing. *Day of Month* is a day.

## Module definitions and instances (`modules.rs`)

A definition is a reusable piece of model with **declared, typed ports**; an instance uses it with its own parameter values and inputs. Before a run, every instance is written out as ordinary variables named `Instance.Variable`; read an output in an equation as `"Instance.Variable"`.

- **in port**: a variable inside the definition whose formula the instance replaces with a formula from the rest of the model.
- **out port**: a variable the rest of the model may read.
- **kind**: `material` (must be a stock or flow) or `information` (anything else). **units**: the connection must carry them (warning if not).
- **parameters**: any constant of the definition can be given another value per instance.

## Files (`io.rs`)

Formats: `.sdm` (native JSON), XMILE, Vensim `.mdl`; detected from the extension, then the first characters. Every read and write also returns a **loss report** (`loss.rs`): each construct dropped, approximated or carried through unchanged. An empty report means nothing was lost. See [Format mapping: XMILE](Format-Mapping-XMILE.md) and [Format mapping: Vensim](Format-Mapping-Vensim.md); for writing equations by hand, [Vensim and Stella side by side](Vensim-Stella-Reference.md).

`io::write_split` writes a **meaning** file (no positions) and a **layout** file (where everything is drawn), so a version-control diff shows model changes, not coordinates.

## Command line: `dyn`

Every command prints JSON; `validate` exits 1 on errors, and any failure exits 2 with `{"ok": false, "error": …}`.

```
dyn info FILE                       counts, settings, loss report
dyn validate FILE [--strict-units]  all checks; exit 1 on errors; strict: a rate may not meet its amount
dyn explain FILE                    the same issues with advice on how to fix each
dyn test FILE                       the model's own checks and conservation only
dyn run FILE [--set Name=Value]… [--series a,b] [--every N] [--csv OUT]
dyn optimize FILE --goal Var [--measure peak] [--maximize] --lever Name:min:max… [--limit "Var<=1000:final"]… [--effort 2] [--apply OUT]
dyn manifest FILE [--draft]         the manifest, or a draft drawn from levers, stocks and checks
dyn sens FILE --var Name [--runs 100] [--spread 0.2] [--seed 1]
dyn importance FILE [--goal G]… [--param P]… [--samples 512] [--seed 1] [--ensemble 30] [--eigen-at T]
dyn dominance FILE [--csv OUT]
dyn recommend FILE --role flow=Orders --role arrival=Arrivals … [--structure supply_line]… [--ensemble 20]
dyn reduce FILE --out OUT [--log CSV] [--goal G]… [--samples 512] [--trajectories 20] [--ensemble 30] [--batch 4] [--st-threshold 0.01]   gates, cut, verify, add back; exit 1 and no file on refusal
dyn verify FULL REDUCED [--goal G]… [--ensemble 50] [--seed 1] [--max-nrmse 0.05]
dyn screen FILE [--goal G]… [--param P]… [--trajectories 20] [--levels 4] [--seed 1] [--tau 0.1] [--csv OUT] [--design]
dyn convert FILE OUT [--format sdm|xmile|mdl]     prints the loss report
dyn diff A B [--runs]               differences in meaning, or in results
dyn list FILE [--kind stock]   dyn get FILE Name   dyn deps FILE Name   dyn loops FILE
dyn ops FILE BATCH.json [--actor name] [--reason text] [--no-gate]   apply a batch, save, append FILE.oplog.jsonl (rejected batches are logged too)
dyn render FILE [--sheet NAME] --out fig.svg [--png [--scale 3]] [--with-caption] [--style FILE]   a sheet as SVG (and PNG), drawn as the app draws it, no display
dyn chart FILE --vars A,B --out chart.svg [--from T0] [--to T1] [--kind line|area|step|stacked|bars] [--title T] [--scenarios A,B|all] [--set N=V]…
dyn layout FILE [--sheet NAME] [--mode tidy|loops] [--loops R1,B2] [--out OUT]   arrange a sheet; positions are written back to the .sdm
dyn cld FILE --from-model [--loops R1,B2] --out cld.sdm [--layout keep|loops]   a causal loop sheet that keeps only the named loops;  dyn cld FILE --list names the loops
dyn set FILE [--sheet NAME] --pos VAR X Y | --polarity A B + | --delay A B [off] | --loop-name B1 "name" | --caption TEXT | --source TEXT
dyn style FILE --apply book.style.json | --show
dyn mcp                             MCP server on stdin/stdout
```

The figure commands (`render`, `chart`, `layout`, `cld`, `set`, `style`) are described, with the style file format, in [Figure library](Figure-Library.md). `render` and `chart` link the headless build of the app's drawing code (`dynamist` with `default-features = false`): `cargo build --release -p dynamist-cli` needs no display and no GUI crate. The editing half is in `core/src/figure.rs` and `core/src/figstyle.rs`.

## MCP server

`dyn mcp` speaks the Model Context Protocol over stdio (newline-delimited JSON-RPC). Add it to an agent's configuration:

```json
{ "mcpServers": { "dynamist": { "command": "/path/to/fc", "args": ["mcp"] } } }
```

Tools: `new_model`, `open_model`, `save_model`, `info`, `list_vars`, `get_var`, `dependencies`, `loops`, `structure_notes`, `describe_api`, `apply_ops` (with a `reason`), `validate`, `explain_problems`, `draft_manifest`, `run`, `optimize`, `sensitivity`, `screen`, `importance`, `dominance`, `diff_with_file`, `undo`, `redo`, `log`. An agent can only change a model through `apply_ops`, so a generated model cannot be saved in a state that does not validate.

## Python

`python/dynamist/__init__.py` wraps `dyn` (standard library only; set `FC_BIN` to the binary):

```python
import dynamist as dyn
m = dyn.Model("tank.sdm")
m.apply([{"op": "set_equation", "name": "Burn rate", "equation": "5"}])   # raises if refused
print(m.validate()["ok"], m.run(series=["Tank"])["series"][0]["last"])
band = m.sensitivity("Tank", runs=200, spread=0.1)
    effects = m.screen(trajectories=20)      # which levers matter for the manifest's goals
```

The figure calls are `m.render(out, sheet=, png=, scale=, with_caption=, style=)`, `m.chart(vars, out, start=, end=, kind=, title=, scenarios=, set=)`, `m.layout(sheet=, mode=, loops=)`, `m.loop_ids()`, `m.cld(out, loops=, layout=)`, `m.set(pos=, polarity=, delay=, loop_name=, caption=, source=)` and `m.style(apply=)`; see [Figure library](Figure-Library.md).

This is a subprocess wrapper, not a compiled (PyO3) binding.

## Statistical charts (optional, seaborn)

`dynamist.plots` draws the charts the analysis functions call for: `sobol` (S1 and ST with confidence bars), `morris` (mu* against sigma, coloured by class), `dominance` (share of time each loop dominates, by polarity) and `fan` (ribbon over an ensemble of runs). Each takes the JSON a function returned, or the path of a saved file, and writes SVG or PNG by file extension. SVG output is byte-identical between runs.

**Charts that are not time series.** `plots.phase(runs, x, y, out)` draws one variable against another (a phase portrait: open circle start, filled end, arrows for direction). `plots.response({label: (xs, ys)}, out, xlabel, ylabel)` draws a goal against a lever, labels at the line ends. `plots.heatmap(result, out, kind="sobol"|"morris")` shows levers by goals from an `importance` or `screen` result. `plots.dominance_timeline(run, series, scores, out)` puts the behaviour over a band of each loop's share of influence on one time axis; `scores` is the CSV or dict of loop scores over time.

**Sweeps and the charts they feed.** `plots.grid(model, series, how, x, xs, y, ys)` runs a model over two levers and returns the goal (`how` = min, max, last, first or mean of a series); `plots.landscape(xs, ys, z, out, …)` draws it as a policy landscape. `plots.tornado_rows(model, series, how, {lever: (low, high)})` feeds `plots.tornado(rows, base, out, …)`. `plots.eigen_path(model, lever, values)` returns the dominant eigenvalue for each value (on a temporary copy of the model), and `plots.root_locus(points, out)` draws it.

**Sankey.** `plots.sankey(model, out)` shows where a conserved quantity goes between stocks over time; the amounts are traced exactly through the model's own flows (`plots.trace`) and refused if they would not balance, and plotly lays the ribbons out. It needs `pip install plotly kaleido` (and Chrome for the export); see [Charting-Ideas](Charting-Ideas.md).

**Budget Sankey.** `plots.budget(model, scenarios, channels, groups, out)` is the "put 100 in, where does it go" chart: one panel per scenario, sources, channels, grouped outcomes, shares in percent, amounts traced exactly through the flows. Needs plotly and kaleido. See [Charting-Ideas](Charting-Ideas.md).

**Sequence diagram.** `plots.sequence(model, {lever: value}, out)` draws how a change spreads through the model as a UML-style sequence diagram (Mermaid): who reacts, in what order, with dashed arrows where feedback loops close. Needs `mmdc` (`npm install -g @mermaid-js/mermaid-cli`).\n\n**Styling.** The charts use the same style file as the diagrams (`book.style.json`): the font, the palette (`stock` navy for the main series, `flow` teal, `aux` ochre, `grid`, `muted`), `width_mm`, `text_scale` and `line_scale`. Call `plots.use_style("book.style.json")` once; without it the defaults equal `book/examples/book.style.json`. Design rules, fixed in the code: no frame, one hairline grid, titles flush left and written as statements, direct labels instead of legend boxes, an optional `source=` line under the figure. A figure and a diagram in the same chapter therefore match.

The core package stays standard-library only. Install the extra when you want these: `pip install -r python/requirements-plots.txt` (seaborn and matplotlib). Without them, importing `dynamist.plots` raises a clear error and nothing else is affected. Model diagrams and loop diagrams still come from `Model.render` and `Model.cld`, which draw the same picture as the app.
